# Phase 8.5 — FK-Relation Introspection + Extract Joining

**Boundary:** Make ManyToOne (and ManyToMany where trivial) Doctrine relations on Kunstmaan page entities first-class citizens of the migration pipeline. Surface them in the LLM-facing knowledge base, join them at extract time, and teach the LLM the relation idiom in its prompt.

## Why this is the next phase (operator framing)

> "What makes the most sense for our generic migrate any Kunstmaan → Craft website approach? I'd also like to use the LLM as much as possible to do the mapping. So for that to work optimally the introspection of both Kunstmaan and Craft must be complete so that reflects in the mapping."

The biggest leverage isn't more LLM cleverness — it's information completeness. Phase 8.4 established that page-builder content flows through extract → transform when the wiring is right (D-17 parser priming + D-18 title heuristic + D-19 mapping.pageParts emitter). Phase 8.5 attacks the next-largest information gap: **page entities that wrap a separate content entity via FK relation are blackboxes to the LLM today.**

## Concrete CQM examples

```php
// src/Entity/Pages/EmployeePage.php
class EmployeePage extends AbstractArticlePage {
    #[ORM\JoinColumn(name: 'employee_id', referencedColumnName: 'id', nullable: true, onDelete: 'SET NULL')]
    #[ORM\ManyToOne(targetEntity: Employee::class)]
    private $employee;
}
```

The page table `lameco_websitebundle_employee_pages` carries only the FK column `employee_id`. The actual displayable fields (name, email, jobTitle, linkedIn, biography, photo) live on `App\Entity\Employee` in `lameco_websitebundle_employee_employees`.

Same shape for `CaseStudyPage→CaseStudyCategory`, likely also `NewsPage→NewsAuthor` / `NewsPage→NewsCategory`, `VacancyPage→…`, etc. This is the dominant Kunstmaan content pattern: a navigable Page wraps a content entity.

The migrator's current shape sees `employee_id: 12` in the extracted payload and has no way to map it to `name: "Jan van Doremalen", email: vandoremalen@cqm.nl, …`.

## Decisions

### D-20 — Surface FK relations in `KnowledgeBase::renderPagesMarkdown` and `renderPagePartsMarkdown`

For each page entity (and pagepart), append a "**Relations**" subsection listing every ManyToOne / ManyToMany from `DoctrineEntityParser->getByFqcn($fqcn)->relations`:

```markdown
### Relations
| property | type | target | FK column | target table | target columns |
|----------|------|--------|-----------|--------------|----------------|
| employee | ManyToOne | App\Entity\Employee | employee_id | lameco_websitebundle_employee_employees | id, name, email, job_title, linked_in, biography, photo_id |
```

`target table` resolved via `DetailTableResolver`; `target columns` via `DoctrineEntityParser` on the target FQCN. This single section answers the LLM's "what's available across this relation" question explicitly.

### D-21 — Extract joins ManyToOne FK relations, embeds related row under `_rel:` namespace

Extend `ExtractService::loadDetailRow` (or a new `joinManyToOneRelations` helper called immediately after) to:

1. Look up `DoctrineEntityParser->getByFqcn($pageFqcn)->relations` for the page being extracted.
2. For each `ManyToOne` relation with a non-null FK column:
   - Read the FK value from the page detail row (e.g. `$detailRow['employee_id']`).
   - If non-null, query the target table by primary key (`SELECT * FROM lameco_websitebundle_employee_employees WHERE id = :id LIMIT 1`).
   - Merge each target column into the page detail row under a namespaced prefix: `_rel:employee.name`, `_rel:employee.email`, etc.
3. The FK column itself stays in the row (operator can still map `employee_id` directly if they want a relation field on the Craft side).
4. Skip silently when target table or row not found (warn at extract level, don't block).

`_rel:` prefix is chosen because:
- Underscore-leading already signals "synthetic" elsewhere in the codebase (`_sourcePartRef`, `_providerType`).
- Colon separator avoids collision with any legacy column name (Doctrine doesn't allow `:` in column names).
- Property name (not target FQCN) gives operator-friendly identity.

ManyToMany relations are out of scope for v1 — they need a join-table walk that's a different shape. Document as a Phase 8.5+ extension if pursued.

### D-22 — Heuristic proposer for `_rel:*` columns

When the residual-column LLM batch encounters a `_rel:<prop>.<col>` column on a page table, it now has a direct `targetHandle` candidate via the parent's Craft entry-type fields. The KB markdown (D-20) already gives it the join shape — no additional prompt scaffolding is strictly required, but the system prompt should mention:

> "Columns with the prefix `_rel:<property>.<column>` are joined from a related entity via Doctrine ManyToOne FK. They may map to ANY field on the parent's Craft entry-type."

Combined with the existing `allowed=[…]` per-residual hint, this gives the LLM what it needs.

### D-23 — Extract emits the relation graph as a separate artifact for downstream tooling

Write `storage/migration/relation-graph.json`:

```json
{
  "App\\Entity\\Pages\\EmployeePage": {
    "manyToOne": [
      {
        "property": "employee",
        "targetEntity": "App\\Entity\\Employee",
        "fkColumn": "employee_id",
        "targetTable": "lameco_websitebundle_employee_employees"
      }
    ]
  },
  …
}
```

Useful for debugging, future verify-style audits, and operators who want to inspect what got joined. Generated during `analyze` (so it's available before any extract run).

### D-24 — `--no-rel-join` CLI flag + `Settings::joinFkRelations` gate

Default: ON. Operator escape hatch when join queries are slow or the related table is huge. Mirrors the Phase 4.1 `--no-seo` / `Settings::seoEnabled` pattern.

## Out of scope for 8.5

- **ManyToMany joins** — different shape, separate phase if needed.
- **Promoting related entities to their own Craft entries** — i.e. instead of embedding Employee fields into EmployeePage, migrate Employee as its own `teamMember` entry and set a relation field on EmployeePage. This is the "right" answer for some patterns but requires per-relation operator intent. Phase 8.6 or 9 territory.
- **Recursive joins** — only one level deep. If `Employee` itself has FK relations, those are not followed.
- **Pagepart sub-fields** — separate Phase 8.6 (block-type sub-field exposure + per-pagepart column proposer). 8.5 only handles page-on-entity FK relations.
