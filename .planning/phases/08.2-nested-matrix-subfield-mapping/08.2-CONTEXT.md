# Phase 8.2 — Nested Matrix-of-Sub-Entry-Type Mapping (Generic)

**Boundary:** Make the LLM proposers and transform stage capable of mapping
direct columns on legacy page tables into Matrix-with-sub-entry-type fields
on Craft entry-types. Addresses the operator's framing for HomePage and
generalises beyond it.

## What the operator asked for

> "Homepage is a good test since it has some kind of header block i think,
> thats not part of the pagebuilder, but it is then a block directly on
> the entry which has sub fields. would be great if llm recognizes that
> and maps if possible in a generic way so it can also work for other
> entries and fields."

## Concrete CQM-rehearsal example

`homePage` (Craft) has two Matrix fields:
- `pageBuilder` — open-ended Matrix for Kunstmaan page-parts (already covered by Phase 6's `proposePagePartBlocks`)
- `headerHome` — Matrix configured `minEntries=1, maxEntries=1`, single inner entry-type `headerHero` with sub-fields `heading`, `subheading`, `image`, `buttonText`, `buttonUrl`

Pre-8.2 the residual-column LLM saw `headerHome` listed as a Matrix field but had no visibility into `headerHero`'s sub-field handles. It returned every HomePage `banner_*` column with `targetHandle: ''` and rationale `"no custom field handle provided in allowed list"`. Result: HomePage transformed payload `fieldValues: []`.

## Decisions

- **D-15 — Dotted-path target handles for nested-Matrix sub-fields.** The LLM may now propose targets like `targetHandle: 'headerHome.heading'`. Two-segment form is canonical (one Matrix-level + one sub-field). Three-segment form (`matrixField.innerType.subField`) is reserved for the rare case where a Matrix has multiple inner entry-types and the auto-pick is wrong — out of scope for v1 of the rule.
  - **CraftKnowledgeBase enrichment:** `renderEntryTypesMarkdown()` walks `craft\fields\Matrix` fields' inner entry-types and emits a `inner '<type>' block — sub-fields:` section listing the `matrix.sub` dotted handles with their field types. `buildFieldIndex()` flattens the dotted handles into the per-entry-type `allowed=[...]` list with `classification: 'matrixSub'` so the LLM sees them in the prompt.
  - **TransformService dotted-path collapse:** after the existing field-loop builds `$fieldValues`, a new pass groups any keys containing `.` by their leading prefix (the Matrix handle), resolves the inner entry-type via Craft fields lookup (with a `matrixInnerTypeMap` test seam), and rewrites `$fieldValues['headerHome'] = ['new1' => ['type' => 'headerHero', 'enabled' => true, 'fields' => [...]]]` — the same Craft 5 native Matrix shape `transformPageBuilder` and the body-wrap emitter already produce.

## Generic by design

The dotted-path mechanism is intentionally schema-agnostic. There is no special-case code for `headerBlock` / `bodyWrapBlock` / `bodyColumn` slot names, no per-project trigger heuristic. Any Matrix field on any Craft entry-type that has at least one inner entry-type with sub-fields participates. This includes — but is not limited to — header / hero blocks, footer-branding blocks, sidebar blocks, FAQ blocks, etc. The rule the operator stated for pageparts ("global, not page-specific") naturally extends here: the Matrix-with-sub-entry-types pattern is a per-entry concern, but the *mechanism* for mapping into it is global.

## Defense-in-depth + skip-existing semantics

- **Operator-set top-level value wins.** If `mapping.yaml` already assigns a flat value to the Matrix field handle (e.g. operator hand-wrote the full Matrix payload for `headerHome`), the dotted-path siblings are dropped with a WARN. No silent merge — that would mutate operator intent.
- **Resolution failures keep dotted keys intact.** If the Matrix handle doesn't exist in Craft, the field exists but isn't a Matrix, or the Matrix has no inner entry-types, the dotted entries are left untouched and the resolver emits a WARN per failure mode. Craft will surface them as unknown handles at save time, giving the operator a clear remediation pointer rather than swallowing data.
- **Multi-inner-entry-type ambiguity surfaces a WARN.** When a Matrix has 2+ inner entry-types, the resolver picks the alphabetically-first handle and warns. Operator can re-mapping with a 3-segment dotted handle to override.

## Out of scope

- **Three-segment dotted handles (matrix.innerType.sub).** v1 only supports two-segment + auto-resolution. The Matrix-with-multiple-inner-entry-types case is rare in practice and the WARN gives the operator a remediation path.
- **Matrix-of-Matrix.** The KB walker is one level deep. Craft permits arbitrary nesting in principle; in practice, content schemas with two-level Matrix nesting are a power-user shape — supporting them would require N-segment dotted handles + recursive payload assembly.
- **Re-running analyze on the CQM rehearsal mapping.** The infrastructure is in place. To exercise the new dotted-path proposals end-to-end against the CQM dump, the operator needs to re-run `kunstmaan-migrator/analyze` (~25 min, ~$1 in Anthropic API spend at current pricing). Not done in 8.2's session — left for the operator's next rehearsal cycle.
