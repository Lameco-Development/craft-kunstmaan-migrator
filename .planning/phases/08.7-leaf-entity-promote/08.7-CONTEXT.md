## Open issues from CQM CaseStudyPage / NewsPage validation

User reported six issues. Status:

### 1. `mode: embed | promote` per-relation choice

⏳ **deferred — broader architecture work.**

Current state: 8.5 D-21 embeds ManyToOne related rows under `_rel:<prop>.<col>` keys. 8.7 D-30/D-31 produce a `relation` handler proposal when the target field is `Entries(from: ...)` or `Assets(kinds: ...)`. The choice between embed vs promote is implicit in the LLM's pick.

Next-up scope: a `mode: embed | promote` key per relation in mapping.yaml; topological extract ordering so promoted leaves migrate before their wrapping pages; new transform-time relation handler that consumes `_rel:<prop>` (property name, not dotted column).

### 2. Compile-stage type validation

⏳ **deferred — focused commit.**

Current state: incompatible (handler, source-shape) pairs land silently. Examples surfaced on CaseStudyPage:
- `caseIntro: { handler: matrix, source: intro }` — Matrix handler on a longtext is wrong; produces silent-empty.

Next-up scope: in `MappingCompiler`, after building each entry's `fields[]`, walk every (handler, source-column-shape) pair. If incompatible, emit a loud warn AND drop the field. Source shapes inferred from the parsed Doctrine column type (varchar / longtext / bigint / datetime / etc.).

### 6. CaseStudyPage `content` lands in `ckeditorSimple` instead of pageBuilder generic block

⏳ **diagnosed — needs a priority decision.**

Current behaviour: the residual-column LLM picks `content → ckeditorSimple` (an entry-level field on `casePage`) because it sees `ckeditorSimple` in the entry-type's `allowed=[…]` set and matches by name. The implicit-content emitter SEPARATELY produces a `__implicit_content__|CaseStudyPage|main` pagepart row, but compile reports `WARN implicit-content row for CaseStudyPage/main skipped: no fields with both sourceProperty and targetHandle filled in` — the implicit row's `fields[]` never got `targetHandle` assigned by the page-part fields LLM (the residual proposer ate the `content` column first).

Next-up scope:
- Option A (heuristic compile pass): when `nodeClasses[fqcn].pageBuilderHandle !== ''` AND there's an accepted `__implicit_content__|<fqcn>|<ctx>` pagepart proposal AND the entry-level fields have a longtext column mapped, demote the entry-level mapping in favor of the implicit pagepart's fields.
- Option B (LLM prompt rule): in the residual-column proposer, when the page entity has `pageBuilderHandle` set AND the column is a longtext / mediumtext content column, prefer DROP over mapping to an entry-level CKEditor field (forcing the implicit-content path).

Option A is more deterministic; Option B is more flexible. Recommendation: Option A first since it doesn't require another LLM run.

Also surfaced: the implicit-content row for CaseStudyPage's `fields[]` (built at AnalyzeController line ~225) only has `sourceProperty` set; `targetHandle` is empty. The page-part fields LLM should fill `targetHandle` against the chosen block-type's allowed fields. Either it's not running for implicit-content rows (scope filter) or the chosen blockType's fields don't include a content destination.

### Side-issues surfaced during validation

These are filter-shape inconsistencies — operator-passed `--entities` is interpreted differently in each stage:

1. **Load-stage filter** (MigrateController::runLoadFromDisk:1441-1456) only matched the simple basename (`CaseStudyPage`). Operators passing `--entities=App\Entity\Pages\CaseStudyPage` (FQCN) saw transform write 47 payloads → load report "no transformed payloads to load". **Fixed in this session** — load now mirrors TransformService's accept-either rule (FQCN OR basename).

2. **Finalize-stage filter** (FinalizeWalker::walk:71) passes `$filters->entities` straight to Craft's `Entry::find()->type()`, which expects **Craft entry-type handles** (e.g. `caseStudyPage`), not Doctrine FQCNs or basenames. Result: `craft\db\QueryAbortedException` (no message). Without `--entities`, finalize ran fine (623 entries / site-pairs walked, 181 CKEditor field reads, 4 rewrites). **Not yet fixed** — proper fix requires translating filter entities to Craft entry-type handles via mapping lookup; needs a separate focused commit.

3. **Finalize error surfacing** swallowed empty `QueryAbortedException` messages. **Fixed in this session** — both `actionIndex` finalize block and `actionFinalize` now emit `<class> <message> @ <file>:<line>`.
