## Open issues from CQM CaseStudyPage / NewsPage validation

### 1. `mode: embed | promote` per-relation choice

⏳ **deferred — broader architecture work.**

Current state: 8.5 D-21 embeds ManyToOne related rows under `_rel:<prop>.<col>` keys. 8.7 D-30/D-31 produce a `relation` handler proposal when the target field is `Entries(from: ...)` or `Assets(kinds: ...)`. The choice between embed vs promote is implicit in the LLM's pick.

Next-up scope: a `mode: embed | promote` key per relation in mapping.yaml; topological extract ordering so promoted leaves migrate before their wrapping pages; new transform-time relation handler that consumes `_rel:<prop>` (property name, not dotted column).

### 6. CaseStudyPage `content` lands in `ckeditorSimple` instead of pageBuilder generic block

⏳ **deeper diagnosis 2026-04-28 — TWO bugs; partial fixes are dangerous.**

`proposePagePartBlocks` IS picking a block-type for the implicit row (verified in mapping.yaml: CaseStudyPage/main got `targetBlockType: generalContentBlock`). What breaks is the column-wiring step that comes next:

**Phase 2 — implicit-row column wiring (root cause of empty `targetHandle`):**

- `AnalyzeController::buildPagePartFieldsContext:1370` calls `$parser->getByFqcn('__implicit_content__')` → null (it's a synthetic marker, not a Doctrine class) → `$pagePartColumns['__implicit_content__']` never populated.
- `LlmClassifier::proposePagePartFields:1539` looks up cols via `$pagePartColumns[$ppFqcn] ?? []` → empty → row falls through to `$passthrough` (line 1542) — LLM never proposes `targetHandle` for implicit rows.
- `MappingCompiler::emitImplicitContentRows:739` then skips the row (`no fields with both sourceProperty and targetHandle filled in`).
- Bonus collision: ALL implicit rows currently share the same `__implicit_content__` cache key, so even if Phase 2 lands without composite keying, CaseStudyPage/ContactPage/ErrorPage implicit rows would overwrite each other's columns.

Phase 2 fix:
1. `AnalyzeController:282-288` (implicit-content emitter) — surface `sqlType` from the page table's column on each `$contentColumns[]` entry.
2. `AnalyzeController::buildPagePartFieldsContext` — special-case `pagePartClass === '__implicit_content__'`: build cols from the row's own `fields[]` (now with sqlType) and key the cache as `__implicit_content__|<parentShort>|<context>`.
3. `LlmClassifier::proposePagePartFields:1539, 1667, 1883` — three callsites that look up `$pagePartColumns[$ppFqcn]` need to compute the composite key for implicit rows.

**Phase 1 — entry-level demote (Option A, the original plan):**

Once Phase 2 lands, the implicit row populates targetHandle and produces a Matrix block from `content`. Without Phase 1, the entry-level `content → ckeditorSimple` proposal also fires → **same source column written to two destinations**. So Phase 1 still needs to ship: when `nodeClasses[fqcn].pageBuilderHandle !== ''` AND an accepted `__implicit_content__|<short>|<ctx>` row references the same source column, drop the entry-level proposal.

**Order matters** — Phase 1 alone loses data (no targetHandle on implicit row, content goes nowhere). Phase 2 alone duplicates content. Ship Phase 2 first, validate, then layer Phase 1.

### Side-issues surfaced during validation

These are filter-shape inconsistencies — operator-passed `--entities` is interpreted differently in each stage:

1. **Load-stage filter** (MigrateController::runLoadFromDisk:1441-1456) only matched the simple basename (`CaseStudyPage`). Operators passing `--entities=App\Entity\Pages\CaseStudyPage` (FQCN) saw transform write 47 payloads → load report "no transformed payloads to load". **Fixed in this session** — load now mirrors TransformService's accept-either rule (FQCN OR basename).

2. **Finalize-stage filter** (FinalizeWalker::walk:71) passes `$filters->entities` straight to Craft's `Entry::find()->type()`, which expects **Craft entry-type handles** (e.g. `caseStudyPage`), not Doctrine FQCNs or basenames. Result: `craft\db\QueryAbortedException` (no message). Without `--entities`, finalize ran fine (623 entries / site-pairs walked, 181 CKEditor field reads, 4 rewrites). **Not yet fixed** — proper fix requires translating filter entities to Craft entry-type handles via mapping lookup; needs a separate focused commit.

3. **Finalize error surfacing** swallowed empty `QueryAbortedException` messages. **Fixed in this session** — both `actionIndex` finalize block and `actionFinalize` now emit `<class> <message> @ <file>:<line>`.
