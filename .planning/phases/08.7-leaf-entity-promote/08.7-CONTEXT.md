### Side-issues surfaced during validation

These are filter-shape inconsistencies — operator-passed `--entities` is interpreted differently in each stage:

1. **Load-stage filter** (MigrateController::runLoadFromDisk:1441-1456) only matched the simple basename (`CaseStudyPage`). Operators passing `--entities=App\Entity\Pages\CaseStudyPage` (FQCN) saw transform write 47 payloads → load report "no transformed payloads to load". **Fixed in this session** — load now mirrors TransformService's accept-either rule (FQCN OR basename).

2. **Finalize-stage filter** (FinalizeWalker::walk:71) passes `$filters->entities` straight to Craft's `Entry::find()->type()`, which expects **Craft entry-type handles** (e.g. `caseStudyPage`), not Doctrine FQCNs or basenames. Result: `craft\db\QueryAbortedException` (no message). Without `--entities`, finalize ran fine (623 entries / site-pairs walked, 181 CKEditor field reads, 4 rewrites). **Not yet fixed** — proper fix requires translating filter entities to Craft entry-type handles via mapping lookup; needs a separate focused commit.

3. **Finalize error surfacing** swallowed empty `QueryAbortedException` messages. **Fixed in this session** — both `actionIndex` finalize block and `actionFinalize` now emit `<class> <message> @ <file>:<line>`.

## New issues raised 2026-04-28 (mid-session validation feedback)

### A. Per-locale title fallback missing for taxonomies

User-visible: EN `caseCategory` entries show `[legacy id N]` instead of the NL title when no `ext_translations` row exists for that legacy id.

Root cause confirmed against CQM DB:
- `caseCategory` entry type's `titleTranslationMethod = "site"` — Craft does NOT propagate the canonical NL title to EN.
- For legacy ids 1, 5, 6, 7, 8, 9 there are zero `ext_translations` rows under any FQCN. `applyGedmoTranslations` enters its D-09 empty-translations branch and re-saves each non-primary site WITHOUT setting `$localized->title`. Stale EN titles (left over from an earlier wrong-mapping run) persist.

Behavioral rule (saved as feedback memory): non-primary sites fall back to the default-language value when there's no per-locale value at all. SEO writers (SEOmatic / Retour) DO NOT follow this rule — they migrate as-is, preserving operator-meaningful empties.

Fix scope: `TaxonomyMigrationService::applyGedmoTranslations` — in BOTH the D-09 empty-translations branch AND the per-locale overlay branch when the locale lacks a title row, set `$localized->title = $entry->title` (and similarly for any other site-translated field) before saving. Roughly 10 LoC. Independent of the LLM — ship anytime.

### B. EmployeePage routing to fallback `contentPage` instead of `teamPages`

User-visible: TeamPages entries empty in Craft because the legacy data isn't reaching them.

Root cause: the analyze-stage entity-level LLM proposal for `App\Entity\Pages\EmployeePage` had `targetEntryType: teamMember` but `targetSection: ''` and `status: needs-review`, so MappingCompiler's fallback path routed it to `Settings::defaultEntryType=contentPage`. Separately, the `App\Entity\Employee` taxonomy proposal had `targetEntryType: teamMember` but `targetSection: ''` so it was being skipped at compile.

Operator-curated fix applied 2026-04-28 (Option 2B per "pages-lead" rule, saved as feedback memory):
- `App\Entity\Pages\EmployeePage` nodeClass row → `targetSection: teamPages`, `status: accepted`. Compile now routes the FQCN to the correct section (fallback list dropped from 15 to 14).
- `App\Entity\Employee` taxonomy row → `status: dropped`, `reason: superseded-by-page`. Page wins; Employee fields will arrive on the EmployeePage entry via `_rel:employee.<col>` embedding (8.5 D-21 ManyToOne).

Remaining work for full migration: populate `EmployeePage.fields[]` with mappings like `role: { source: _rel:employee.job_title }`, `linkEmail: { source: _rel:employee.email }`, etc. Cheapest path is re-running `analyze` after credits restored — the LLM should pick these now that it sees the entity-level proposal accepted with `targetSection=teamPages`.
