# Phase 12 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | Craft CMS 5 Control Panel native UI |
| Preset | not applicable |
| Component library | Craft CP native layouts, utilities, tabs, tables, forms, buttons, notices, badges, progress/job affordances |
| Icon library | Craft CP native icons only; keep current Utility icon `shuffle` unless a native migration/queue icon is already available |
| Font | Craft CP native system font stack; do not introduce plugin-specific web fonts |

### Source Decisions

- Source: `12-CONTEXT.md` D-01, D-02, D-03 — expand the existing `KunstmaanMappingUtility` into a tabbed Craft Utility; no top-level CP section/nav in this phase.
- Source: Craft UI constraints from phase prompt — prefer Craft CP native layout, tables, forms, buttons, notices, tabs, and status colors over bespoke styling.
- Source: existing `templates/_mapping/index.twig` — current UI already uses simple Craft-compatible forms, `.btn`, `.submit`, `csrfInput()`, `actionInput()`, and utility-local classes.
- Source: existing `src/templates/_settings.twig` — settings are a Craft settings fragment using `_includes/forms` macros; keep this pattern.

### Design-System Contract

1. Use Craft CP chrome and Utility page layout; do not build a custom app shell.
2. Use native Craft tab navigation or Craft-compatible tab-like subnavigation within the existing Utility content.
3. Use Craft form macros (`_includes/forms`) for settings and structured controls wherever possible.
4. Use Craft `.btn`, `.submit`, `.small`, `.warning`, `.error`, `.notice`, `.pane`, `.data`, `.fullwidth`, `.select`, `.text`, `.lightswitch`, and native CP status styles before adding custom CSS.
5. Custom CSS is allowed only for local layout glue:
   - tab panel spacing,
   - readiness summary grid,
   - run record metadata layout,
   - mapping row density,
   - log/artifact monospace blocks.
6. No shadcn initialization. This is a PHP/Craft CMS Control Panel surface, not React/Next/Vite.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon/text gaps, status dot gaps, compact inline metadata |
| sm | 8px | Button groups, badge spacing, field-adjacent helper text, compact table cell padding |
| md | 16px | Default panel padding, row card padding, form group gaps |
| lg | 24px | Tab content top spacing, section breaks within a tab, dashboard grid gaps |
| xl | 32px | Major groups inside the Utility, separation between high-risk panels and regular panels |
| 2xl | 48px | Empty-state vertical padding, major dashboard-to-detail separation |
| 3xl | 64px | Reserved for page-level vertical breathing room only; avoid inside dense CP tables |

Exceptions: Native Craft CP controls may retain their built-in sizing. Icon-only or high-risk action targets must have at least a 36px hit area; live/destructive confirmation submit rows must provide at least 44px vertical target comfort through button sizing or row padding.

### Spacing Application

- Dashboard/readiness cards: `md` internal padding, `lg` grid gap.
- Tabs: `lg` space below tab bar before content.
- Data tables: use Craft native table rhythm; do not add bulky card styling to every table row.
- Mapping review rows: keep existing card pattern but standardize to `md` padding and `md` bottom margin.
- Gate checklists: `sm` vertical spacing between gate rows; `md` spacing before remediation block.
- Dangerous/reset panel: `xl` top margin from regular controls; `md` internal padding; destructive action separated from neutral explanatory copy by `md`.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label | 12px | 600 | 1.4 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.2 |

### Typography Contract

1. Use exactly these four type roles for plugin-authored UI.
2. Use Craft CP native heading styles where available; otherwise match the table above.
3. Use `Label` for:
   - gate names,
   - status labels,
   - table column headings,
   - compact metadata labels.
4. Use `Body` for explanatory copy, instructions, logs summaries, and remediation instructions.
5. Use `Heading` for tab-section titles such as “Readiness”, “Latest run”, “Mapping coverage”, “Live gates”.
6. Use `Display` only for dashboard summary numbers, such as total runs, unresolved mapping rows, or current run progress percentage.
7. Monospace values use Craft/native monospace or `ui-monospace, SFMono-Regular, Menlo, Consolas, monospace` at 12px, weight 400, line-height 1.5.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | Craft CP background / `#f3f7fc` equivalent | Utility page background and non-emphasized page surface |
| Secondary (30%) | White / `#ffffff` | Panes, cards, table surfaces, mapping row cards, run detail panels |
| Accent (10%) | Craft CP submit blue / `#0d78f2` equivalent | Primary queued action buttons, active tab indicator, progress links, “View run” links |
| Destructive | Craft CP destructive red / `#cf1124` equivalent | Live migration warnings, truncate/reset controls, destructive confirmations, blocked gate failures |

Accent reserved for: active tab state, primary CTA for the currently selected safe action, run progress emphasis, focused remediation links, and “View details” links from run tables. Do not use accent for every button or every status badge.

### Semantic Status Colors

Use Craft CP native status/notice colors where possible:

| State | Visual Treatment |
|-------|------------------|
| Ready / passed / complete | Native success status; green status dot/check badge |
| Running / queued | Accent progress indicator plus neutral “Queued”/“Running” badge |
| Warning / needs review | Native warning/yellow notice; used for mapping warnings, unsupported accepted rows, recent compile warnings |
| Blocked / failed / fatal | Native error/red notice; used for failed gates, production hard-block, missing elevated session, failed run |
| Unknown / unverifiable | Neutral gray badge plus blocking remediation where live execution is concerned |
| Informational | Native info/notice style; used for CLI command suggestions and artifact paths |

### Color Safety

- Live migration blocked states must be red/error, not yellow/warning.
- Unverifiable live gates are blocking and must be visually grouped with errors.
- Dry-run warnings may use warning color and still allow dry-run completion.
- Mapping rows with `unsupported`, fatal warning, or unsafe status must not appear visually identical to accepted rows.

### Tone

- Use direct operator language.
- Avoid marketing phrasing.
- Prefer “blocked”, “queued”, “running”, “failed”, “completed”, “needs review”.
- Always pair a blocked state with the next remediation step.
- Never imply CP live execution is safe unless all gates have passed.

## Phase 12 Surface Contract

### Overall Navigation

Phase 12 expands the existing Craft Utility into a tabbed migration console.

Use this tab order:

1. **Readiness**
2. **Analyze**
3. **Mapping**
4. **Compile**
5. **Runs**
6. **Reports**
7. **Danger Zone**

Rules:

- Keep the Utility under Craft Utilities.
- Do not add a top-level CP nav item.
- The existing mapping review UI becomes the **Mapping** tab.
- The settings page remains plugin settings, not a console tab, except for links from readiness/remediation.
- Tabs must preserve active state via query param, route segment, or Craft-native tab mechanism.
- Filters should remain in the URL where possible so reload/back/bookmark behavior is predictable.

### Readiness Tab

Purpose: one-screen operator summary before any action.

Required sections:

1. **Environment**
   - Environment name.
   - Production status.
   - Admin status.
   - Elevated session status when checking high-risk actions.
2. **Connectivity**
   - Legacy DB reachability.
   - Anthropic API key presence only; never display key value.
   - Kunstmaan source path validity.
   - Storage/migration writability.
3. **Mapping & Compile**
   - Mapping file path.
   - Mapping coverage summary.
   - Unsupported/warning row counts.
   - Latest compile timestamp.
   - Fatal compile warning count.
4. **Queue**
   - Queue component available.
   - Worker/readiness status if verifiable.
   - If unverifiable, show blocked live status plus CLI remediation.
5. **Latest run**
   - Stage, mode, status, progress, started/finished timestamps.
   - Link to run detail.

Visual contract:

- Primary visual focal point: the Readiness status summary, with blocked gates shown first.
- Secondary visual focal point: the single enabled primary action, **Queue dry run**, when gates pass.
- Use a 2-column responsive card grid on wide screens; single column in narrow CP content.
- Each card gets a clear status badge: Passed, Warning, Blocked, Unknown.
- Blocked items must appear before warnings inside each card.
- Use one primary CTA in this tab: **Queue dry run** only when dry-run gates pass.

### Analyze Tab

Purpose: allow safe queued analyze only with explicit AI confirmation.

Required controls:

- Entity filter.
- Locale filter.
- Since date filter.
- AI confirmation checkbox.
- Primary CTA: **Queue analyze**.
- Disabled state if Anthropic API key missing.
- Show equivalent CLI command.

Interaction contract:

1. The **Queue analyze** button is disabled until:
   - admin user is confirmed,
   - non-production environment is confirmed,
   - Anthropic API key presence is confirmed,
   - AI confirmation checkbox is checked.
2. Submit creates a run record and queues a job.
3. The web request must not run analyze inline.
4. On success, redirect to run detail or Runs tab with success notice.
5. On failure, show inline gate errors and preserve selected filters.

Copy:

- Checkbox: “I understand analyze may send schema and mapping context to Anthropic.”
- Disabled missing-key copy: “Analyze is unavailable because no Anthropic API key is configured.”

### Mapping Tab

Purpose: improve the existing `mapping.yaml` review while keeping `mapping.yaml` canonical.

Required controls:

- Page/entity selector.
- Status filter:
  - All
  - Proposed
  - Needs review
  - Accepted
  - Dropped
  - Unsupported
  - Warning
- Kind filter:
  - All
  - Column
  - Page part
  - Node class
  - Taxonomy
  - Data provider, if present
- Warning/finding filter:
  - All
  - Fatal
  - Warning
  - Unsupported
  - No findings
- Search input for source table, source column, FQCN, target handle, handler.
- Batch selection checkboxes.
- Batch actions:
  - Accept selected
  - Mark needs review
  - Drop selected
  - Accept warnings explicitly

Row visual contract:

- Preserve the current card-per-row option for edit-heavy rows, but tables may be used for overview/filter lists.
- Every row must show:
  - row index,
  - kind,
  - status,
  - source summary,
  - target summary,
  - handler,
  - finding severity,
  - rationale if present.
- Warning/unsupported rows must show a visible reason before edit controls.
- Accepted rows with warnings must not be visually identical to clean accepted rows.
- Dropped rows must keep the drop rationale visible.

Editing contract:

- Target/handler editing remains structured form fields with datalist/select suggestions.
- All writes use POST, CSRF, and controller validation.
- Saves update canonical `mapping.yaml` through atomic helpers.
- No draft mapping file.
- No parallel database-backed mapping source.
- Batch destructive actions require typed confirmation when dropping many rows or accepting unsupported/warning rows explicitly.

Primary CTA for this tab:

- **Save mapping changes** for row edit.
- Batch primary action changes according to selected action, but destructive batch buttons are not styled as submit-blue.

### Compile Tab

Purpose: queue compile and surface compile health.

Required sections:

1. Latest compile summary:
   - timestamp,
   - status,
   - fatal warnings,
   - warning count,
   - artifact paths,
   - link to logs/report.
2. Compile readiness:
   - mapping file exists,
   - mapping coverage,
   - Craft target drift,
   - unsupported rows.
3. Controls:
   - filters/options matching CLI where phase supports them,
   - primary CTA **Queue compile**,
   - equivalent CLI command.

Interaction contract:

- Compile runs as a queued job, not inline.
- Compile is allowed when non-production and admin checks pass.
- Fatal compile warnings block CP live migration until resolved.
- Successful compile updates live gate state.

### Runs Tab

Purpose: first-class run records, not just Craft’s generic queue UI.

Required run table columns:

1. Run ID
2. Stage
3. Mode
4. Status
5. Filters
6. Initiated by
7. Queue job ID
8. Progress
9. Started
10. Finished
11. Artifacts
12. Actions

Run statuses:

- Draft/preparing
- Queued
- Running
- Succeeded
- Failed
- Cancelled, if supported
- Blocked

Modes:

- Analyze
- Compile
- Dry run
- Live
- Verify/report
- Cleanup/reset

Required row actions:

- View details
- View log
- View artifacts
- Copy CLI command
- Retry safe stage, when applicable

Run detail contract:

- Header summary with status, progress, stage/mode.
- Gate snapshot used when the run was queued.
- Filters/options snapshot.
- Initiating admin.
- Queue job IDs.
- Timestamps.
- Log path and latest log excerpt.
- Artifact path list.
- Failure details.
- Summary JSON rendered as readable key-value/table blocks, not raw dump by default.
- Raw JSON may be available in a collapsed `<details>` block.

Progress contract:

- Queued: neutral badge.
- Running: progress bar or percent text using accent.
- Succeeded: success badge.
- Failed/blocked: error badge and remediation copy.
- Refresh affordance: normal CP refresh/reload is acceptable; no bespoke real-time polling required unless already easy through Craft/Yii assets.

### Dry Run and Live Run Controls

Dry run belongs in the Runs tab or Readiness tab as the primary safe migration action.

Dry-run required gates:

- non-production,
- admin user,
- mapping file exists,
- recent compile exists,
- no fatal compile warnings,
- required filters/options valid,
- queue can accept jobs.

Dry-run CTA:

- **Queue dry run**

Live run must be visually and interactively separated from dry run.

Live required gates:

1. Non-production environment.
2. Admin user.
3. Elevated session.
4. Typed confirmation phrase.
5. Successful dry run for same filters/options.
6. Recent compile with no fatal warnings.
7. Queue worker readiness.
8. Backup acknowledgement checkbox.
9. Mapping coverage has no unsupported/warning rows unless explicitly accepted.
10. Production hard-block enforced independently in CP controllers and queue jobs.

Live interaction contract:

- Live panel is collapsed or visually separated by default.
- If any gate fails or is unverifiable, the live CTA is disabled.
- If a gate cannot be automatically verified, CP live execution is blocked; show CLI/remediation instead.
- There is no “warn but continue” CP override for unverifiable gates.
- Typed phrase: `MIGRATE LIVE`.
- Backup checkbox text: “I have a restorable database and asset backup for this environment.”
- Primary destructive CTA label: **Queue live migration**.
- Destructive CTA uses Craft destructive styling, not accent blue.

### Reports Tab

Purpose: surface existing artifacts without inventing a new reporting model.

Required artifact groups:

- `REPORT.md`
- `VERIFY-<timestamp>.md`
- `PAGE-ROOTED-COVERAGE.md`
- `MAPPING-AUDIT.md`
- graph artifacts:
  - `kunstmaan-schema.json`
  - `craft-schema.json`
  - relation graph artifacts, if present
- run-specific logs and reports under `storage/migration`

Visual contract:

- Use a table/list of artifacts with:
  - name,
  - type,
  - modified date,
  - associated run,
  - action link.
- Markdown artifacts render in a readable CP pane when practical.
- JSON artifacts show summary metadata first and raw JSON in collapsed view.
- Artifact paths must remain visible/copyable for external inspection.

### Danger Zone Tab

Purpose: isolate destructive/high-risk controls.

Required actions, only if implemented in this phase:

1. Truncate/reset migration state.
2. Cleanup old run artifacts/logs.
3. Clear failed queued run state, if needed.
4. Batch drop mapping rows, if not kept solely inside Mapping tab.

Visual contract:

- Use red/destructive heading or warning notice.
- Each destructive action is in its own panel.
- Show exactly what will be deleted or changed.
- Require elevated session.
- Require typed confirmation phrase.
- Use POST, CSRF, controller validation.
- Never make destructive buttons visually primary-blue.

Copy:

- Section heading: “Danger Zone”
- Intro: “These actions can remove migration state, logs, artifacts, or reviewed mapping decisions. They require an elevated session and typed confirmation.”
- Reset phrase: `RESET MIGRATION STATE`
- Cleanup phrase: `DELETE ARTIFACTS`

## Accessibility Contract

1. All tabs must be keyboard reachable and expose active state.
2. Every form input must have a visible label.
3. Status must not rely on color alone; include text labels such as “Passed”, “Blocked”, “Warning”.
4. Error notices must be programmatically near the relevant form section.
5. Disabled actions must include visible reason text.
6. Confirmation phrase fields must declare the required phrase in nearby helper text.
7. Tables must use real table semantics for run/artifact lists.
8. Log excerpts must preserve whitespace but remain horizontally scrollable instead of breaking layout.
9. Buttons with destructive consequences must include specific labels; no generic “Submit” for high-risk actions.
10. Focus order must follow tab content order: filters → summary → table/list → row actions → pagination.

  - `method="post"`,

  - success for queued/saved actions,
  - error for failed validation,
