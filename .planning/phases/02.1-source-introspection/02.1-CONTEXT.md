# Phase 02.1: Kunstmaan Source Introspection - Context

**Gathered:** 2026-04-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 02.1 makes the Kunstmaan **source codebase** the canonical input for content-schema discovery. The DB alone cannot reconstruct (a) project-prefixed table names, (b) polymorphic page-part identity (Doctrine single-table inheritance discriminators), or (c) the page → context → allowed-page-part-classes structure that lives in `Entity/Pages/*.php::getPagePartAdminConfigurations()` + `config/kunstmaancms/pageparts/*.yml`. By the end of Phase 02.1:

1. The plugin reads a Kunstmaan source path (env var + Settings ladder) and FAILs every legacy-reading command if the path is not configured. Greenfield-fallback (`kuma_*` LIKE) is dropped.
2. Two scanners (`KunstmaanSourceScanner` for Doctrine schema; `KunstmaanPageStructureScanner` for page-parts) fire at the top of `analyze`, producing schema-dump enrichment + `storage/migration/pageStructure.json`.
3. Eight v1 brownfield classes are ported (DoctrineEntityParser, DetailTableResolver, KnowledgeBase, BodyScanColumnFinder, MediaFkScanner, TopologicalOrderer, BlockAvailabilityValidator, plus the in-flight CoverageAuditor + MappingAuditor reconciliations) into `src/source/` and `src/mapping/`.
4. `mapping.yaml` grows a new row kind (`pagePart`) alongside the existing column-level rows; identity tuple extends accordingly. The `map` rubber-stamp loop walks both kinds uniformly.
5. `MappingAuditor` gains `BlockAvailabilityValidator` as a new finding kind (warn-by-default, `--audit-strict` elevates).
6. `HeuristicProposer` gains an entity-aware heuristic (slot 1.5) and `LlmClassifier` receives `KnowledgeBase` Markdown in its prompts (replacing the current `'', ''` placeholders).
7. `RECONCILIATION.md` documents every v1 rule's disposition (ported / dropped intentionally / dropped accidentally → patched in this phase) for both `CoverageAuditor` (102 LOC v2 vs 482 LOC v1) and `MappingAuditor` (172 LOC v2 vs 647 LOC v1).
8. Doctor's 5th check verifies the source path exists, contains `src/Entity/`, and (when present) `config/kunstmaancms/pageparts/`.

**Out of scope for Phase 02.1** (deferred):
- Phase 3 transform/load consumers of `pageStructure.json` (Matrix-field construction, page-part property → block-field handlers).
- Per-class escape-hatch mapper system (`AbstractPagePartMapper` / `AbstractNodeClassMapper` / `DeclarativeMapperDriver`) — Phase 3.
- CKEditor token resolution (`[NT<id>]` / `[M<id>]`) — Phase 3 finalize.
- Source-scan caching across invocations (`source-scan.json` artifact + `--rescan-source` invalidation) — defer until profiling justifies.
- Heuristic-2 name-match auto-promotion of page-part rows (HeaderPagePart → header) — page-part rows always start `needs-review` in v1.0 (D-35).
- Multi-list `--since` column candidates (`date`, `publishDate`, `published_at`) — Phase 2 / D-11 default carries forward.

## Implementation Decisions

### Source path acquisition & fallback semantics

- **D-30:** **`KUNSTMAAN_SOURCE_PATH` env var primary; `Settings::kunstmaanSourcePath` overrides via `??=` ladder.** Mirrors Phase 1 / D-12 pattern (used for `legacyDb*`, `anthropicApiKey`, etc.). Settings model gets a new property (declared like `llmModel` / `llmTimeout` were declared upfront in Phase 1 / D-15).

- **D-31:** **`KUNSTMAAN_SOURCE_PATH` is REQUIRED for analyze.** Doctor's 5th check FAILs (not WARNs) when unset; analyze hard-fails as the first statement of `actionIndex` (gate-first idiom, Phase 1 / D-20). **Patches ROADMAP.md Phase 02.1 success criteria 1 + 3** — drop "Degrades gracefully when path unset (greenfield mode → current `kuma_*` LIKE behavior)" and the "falls back to `LIKE 'kuma_%'` (or `Settings::legacyDbTablePrefix`) otherwise" wording. Greenfield mode is dropped; Phase 02.1 is the new floor.

- **D-32:** **Drift detection (DB↔scan mismatch) is WARN by default, `--source-strict` opt-in elevates to fail.** Mirrors Phase 2 / D-16 mapping-audit pattern. Findings emitted to console + persistent artifact (likely a `Drift` section in `MAPPING-AUDIT.md` or a sibling `DRIFT-REPORT.md` — researcher to choose). Two drift categories: (i) DB has table not in scan output (project tables not in source — e.g. legacy SQL-only tables), (ii) scan declares table missing from DB (entity defined but never persisted).

- **D-33:** **`KunstmaanSourcePathResolver` Yii Component** (LegacyDbService analog) owns `??=` env fallback + path validation (exists, readable, contains `src/Entity/`). Scanners receive a resolved absolute path. Single source of truth for path resolution; doctor's 5th check uses the same resolver.

### mapping.yaml schema extension for page-parts

- **D-34:** **Page-part mappings are a NEW row kind in the same flat `proposals:` list.** Each row carries `kind: column | pagePart` discriminator. Column rows keep their existing shape (Phase 2 / D-01) with implicit/explicit `kind: column`. Page-part rows nest per-property mappings inline. Identity tuple extends:

  - Column rows: `(kind, table, column, targetEntryType)` — extended from Phase 2 / D-04 with explicit kind.
  - PagePart rows: `(kind, pagePartClass, parentPageClass, context, targetEntryType)`.

  Reference shape:

  ```yaml
  proposals:
    # column-level (Phase 2 shape, kind explicit)
    - kind: column
      table: kuma_news_page
      column: body_richtext
      targetEntryType: newsArticle
      targetHandle: body
      handler: ckeditor
      status: accepted
      confidence: high
      rationale: 'auto-match: sqlType=LONGTEXT → richtext field'
      fillRate: 0.94
      sqlType: LONGTEXT
      samples: [...]

    # page-part (new kind)
    - kind: pagePart
      pagePartClass: HeaderPagePart
      sourceTable: kuma_main_pageparts
      parentPageClass: NewsPage
      context: main
      targetEntryType: newsArticle
      targetMatrixField: body
      targetBlockType: header
      fields:
        - { sourceProperty: title, targetHandle: heading, handler: plain }
      status: needs-review
      confidence: medium
      rationale: 'page-part class HeaderPagePart in NewsPage context "main"'
  ```

  **Patches Phase 2 / D-04 merge identity tuple.** `MappingFile::merge` keys on the kind-prefixed tuple. Existing accepted/dropped rows preserved verbatim.

- **D-35:** **Page-part rows initial status = `needs-review`.** No auto-accept on name match in v1.0. Operator rubber-stamps every page-part class through the `map` loop. (Heuristic-2 name-match extension to page-parts is deferred; rationale: page-part → block-type mapping is a domain decision, no deterministic heuristic strong enough.)

- **D-36:** **`BlockAvailabilityValidator` extends `MappingAuditor` as a new finding kind.** Same warn-by-default + `--audit-strict` elevation as Phase 2 / D-16. Findings join the existing three (`missing-entry-type`, `missing-handle`, `handler-classification-mismatch`). Roadmap criterion 15 satisfied through `MappingAuditor`. Coverage gate (Phase 2 / D-14) extends: every page-part class with at least one DB row in scope must have a `(kind=pagePart, ...)` row with `status ∈ {accepted, dropped}` in mapping.yaml. Unmapped page-part classes block `migrate --live`.

### v1↔v2 reconciliation methodology

- **D-37:** **Rule-by-rule structured diff.** For each ported v1 file, enumerate every distinct rule (every `if`-branch, every constant, every threshold) and classify as: (a) **ported** [cite v2 file:line], (b) **dropped intentionally** [cite reason — usually "v2 architectural decision (single mapping.yaml; runtime-zero-AI; CLI-only; etc.)"], (c) **dropped accidentally** [add to v2 in this phase]. Methodical and slow but produces a survivable artifact.

  Files in scope:
  - `src/bridge/schema/knowledgebase/CoverageAuditor.php` (482 LOC) vs `src/mapping/CoverageAuditor.php` (102 LOC, Plan 02-05).
  - `src/bridge/mapping/MappingValidator.php` (647 LOC) vs `src/mapping/MappingAuditor.php` (172 LOC, Plan 02-05).
  - Plus the seven verbatim ports (DoctrineEntityParser 366, DetailTableResolver 280, KnowledgeBase ~68KB, BodyScanColumnFinder 100, MediaFkScanner 100, TopologicalOrderer 130, BlockAvailabilityValidator ~200) — for these the methodology is "port byte-for-byte, then reconcile any reshape required by v2 namespace flatness."

- **D-38:** **Acceptance bar = feature parity.** Default stance: every v1 rule lands in v2 unless explicitly dropped with documented rationale. v1 shipped against the CQM rehearsal — that signal is load-bearing. The LOC delta between v2-fresh-write and v1 narrows toward v1's totals as accidental drops surface and get patched. Conservative posture; preserves "shipped against CQM" confidence.

- **D-39:** **`.planning/phases/02.1-source-introspection/RECONCILIATION.md`** is the canonical artifact. Generated during plan-phase research (gsd-phase-researcher reads both v1 originals and Plan 02-05's fresh writes). Cited by execute-phase plans as the reference for which rules to add. Verified during phase verification (the verifier checks that every "dropped accidentally" entry has a matching v2 patch).

### Scanner architecture & pipeline integration

- **D-40:** **Two scanners.** `KunstmaanSourceScanner` is the Doctrine annotation parser; it absorbs DoctrineEntityParser + DetailTableResolver + M2M discovery + BodyScanColumnFinder + MediaFkScanner + TopologicalOrderer (these last three don't strictly need source code but their discovery surface belongs in the source slot per D-41). `KunstmaanPageStructureScanner` reads PHP `getPagePartAdminConfigurations()` + YAML `config/kunstmaancms/pageparts/*.yml`. Two output shapes:

  - Schema-dump enrichment: a structured table list consumed by `SchemaDumper` (replaces the current `LIKE 'kuma_%'` query).
  - `storage/migration/pageStructure.json`: per-Page-entity record `{ tableName, contexts: [{ name, allowedPagePartClasses: [{class, table}] }], templates, possibleChildTypes }`.

- **D-41:** **`src/source/`** is the top-level slot. All source-introspection classes flatten here:

  ```
  src/source/
    KunstmaanSourceScanner.php
    KunstmaanPageStructureScanner.php
    KunstmaanSourcePathResolver.php
    DoctrineEntityParser.php (port)
    DoctrineEntityInfo.php (port)
    DoctrineColumnInfo.php (port)
    DoctrineRelationInfo.php (port)
    DetailTableResolver.php (port)
    KnowledgeBase.php (port)
    BodyScanColumnFinder.php (port)
    MediaFkScanner.php (port)
    TopologicalOrderer.php (port)
  ```

  `BlockAvailabilityValidator` lives under `src/mapping/` alongside the other auditor extensions. Mirrors v1's `src/kunstmaan/schema/` shape but at v2's flatter top level (no `src/kunstmaan/` enclosing dir).

- **D-42:** **Scanners fire BEFORE SchemaDumper in AnalyzeController.** New step order (was 8 steps after Plan 02-05; becomes 11):

  1. NeverProduction gate (Phase 1 / D-20)
  2. FilterFactory.fromCli + LocalePreflight.ensure
  3. **KunstmaanSourceScanner.scan** (new — produces table list + entity index)
  4. **KunstmaanPageStructureScanner.scan** (new — produces pageStructure)
  5. **pageStructure.json write** (new — writeAtomicJson to storage/migration/)
  6. SchemaDumper.dump (now consumes discovered table list)
  7. HeuristicProposer.propose (now uses entity-aware heuristic 1.5 — D-44)
  8. LlmClassifier.batchPropose (now passes KnowledgeBase markdown — replaces `'', ''` placeholders)
  9. MappingFile.merge (skip-existing per Phase 2 / D-04, with extended identity tuple per D-34)
  10. MappingAuditor.audit (now includes BlockAvailabilityValidator — D-36)
  11. ReportBuilder.render → REPORT.md

- **D-43:** **No source-scan caching.** Re-run every analyze invocation. Scan is fast (parse PHP files + YAML — typical Kunstmaan project <500 source files; expected wall time 200-500ms). No cache invalidation problems. Defer caching machinery (`source-scan.json` artifact + mtime-stat-on-read or `--rescan-source` flag) until profiling shows scan time matters.

### Heuristic enrichment

- **D-44:** **New heuristic 1.5 (between zero-fill and exact-name):** column → entity property → Craft field handle, scoped by entity-class context. The column belongs to entity X (e.g. `NewsPage`), entity X maps to Craft entry type Y (e.g. `newsPages`), property name on X matches a field handle on Y. Higher confidence than the global exact-name heuristic (because it's scoped, not global). Status: **heuristic-high → `accepted`** (Phase 2 / D-02 mapping). Renumbers existing heuristics 2-9 to 3-10 in `HeuristicProposer`.

  The DUTCH_ALIASES heuristic (already retired in Phase 2 / D-29) stays retired — D-44 doesn't resurrect it.

### Claude's Discretion

- **Drift artifact location:** Whether D-32 drift findings land in `MAPPING-AUDIT.md` (sibling section) or a dedicated `DRIFT-REPORT.md`. Researcher decides based on whether drift findings are conceptually mapping-audit findings (probably) or a separate concern.
- **`pageStructure.json` field-level shape:** Top-level grouping (by Page entity FQCN vs by table name vs flat list), inheritance-chain inclusion (e.g. `NewsPage extends AbstractArticlePage extends AbstractPage` — show full chain or just leaf?), source path provenance (record which YAML file each context came from). Researcher to flesh out using the CQM source as reference.
- **PHP `getPagePartAdminConfigurations()` parser strategy:** AST-based (nikic/php-parser) vs regex/heuristic vs `eval`-and-introspect. AST is the right answer (regex breaks on non-trivial PHP; eval is a security hazard). Researcher to confirm v1 uses AST and port the approach.
- **Heuristic 1.5 entity → entry-type resolution:** How does the heuristic know which Craft entry type `NewsPage` maps to? Likely via Doctrine entity FQCN → table name → existing accepted-row's `targetEntryType` (i.e. lookup mapping.yaml itself for the Page-entity-level decision and propagate to its column-level rows). Researcher to confirm or propose alternative.
- **YAML config absence behavior:** When `config/kunstmaancms/pageparts/` is missing entirely, `KunstmaanPageStructureScanner` falls back to PHP-only scan (read `getPagePartAdminConfigurations()` returns and infer the contexts without the YAML allowed-class lists). Doctor's 5th check WARNs, doesn't FAIL. Roadmap criterion 10 already permits this.
- **Doctrine annotation syntax coverage:** Both PHP 8 attributes (`#[ORM\Table(name: '…')]`) AND legacy docblock annotations (`@ORM\Table`). v1's DoctrineEntityParser supports both — port verbatim.
