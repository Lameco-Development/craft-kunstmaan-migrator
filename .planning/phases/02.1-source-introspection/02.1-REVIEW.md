## Warnings

### WR-01: `MapController` entity filter silently excludes every `kind: pagePart` row

**File:** `src/console/MapController.php:662-675` (and call sites at `:120` `applyEntitiesFilter` + `:137` walk-order builder)

**Issue:** `matchesEntitiesFilter()` reads `$row['table']` only, but page-part rows produced by `MappingFile::buildPagePartRow()` (see `src/mapping/MappingFile.php:140-141`) carry `sourceTable` / `parentPageClass` instead — the `table` key is absent. When the operator runs `php craft kunstmaan-migrator/map --entities=NewsPage`, every `kind: pagePart` row hits an empty `$table` string, fails `str_starts_with($table, 'kuma_news_page')`, and is silently dropped from both `applyEntitiesFilter()` (line 645) and the interactive `walkOrder` (lines 134-139). Result: the operator never sees page-part rows when an `--entities` filter is set, even though those rows are exactly the page-class subset they're filtering for.

PATTERNS section 16 specs the two-mode walker (column vs pagePart dispatch) but doesn't address the filter — this looks like an oversight, not a documented Rule-3 reshape.

**Fix:** Branch the filter on row kind. For `kind: pagePart`, match against `parentPageClass` (the natural Page-entity attribute) and/or `sourceTable`:

```php
private function matchesEntitiesFilter(array $row, MigrationFilters $filters): bool
{
    if ($filters->entities === []) {
        return true;
    }
    $kind = (string) ($row['kind'] ?? 'column');
    if ($kind === 'pagePart') {
        $parentPageClass = (string) ($row['parentPageClass'] ?? '');
        $sourceTable     = (string) ($row['sourceTable'] ?? '');
        foreach ($filters->entities as $e) {
            if ($parentPageClass === $e || $parentPageClass === ltrim(strrchr('\\' . $parentPageClass, '\\') ?: '', '\\')) {
                return true;
            }
            $snake = strtolower(preg_replace('/(?<!^)[A-Z]/', '_$0', $e) ?? $e);
            if ($sourceTable !== '' && str_starts_with($sourceTable, 'kuma_' . $snake)) {
                return true;
            }
        }
        return false;
    }
    // existing column-row logic unchanged
    $table = (string) ($row['table'] ?? '');
    foreach ($filters->entities as $e) {
        $snake = strtolower(preg_replace('/(?<!^)[A-Z]/', '_$0', $e) ?? $e);
        if (str_starts_with($table, 'kuma_' . $snake)) {
            return true;
        }
    }
    return false;
}
```

Add a unit test along the lines of `MapController::matchesEntitiesFilter` keeping pagePart rows whose `parentPageClass` matches an `--entities` value.

### IN-01: `KunstmaanCoreTables` missing `declare(strict_types=1);`

**File:** `src/source/KunstmaanCoreTables.php:1-3`

**Issue:** Every other file under `src/source/` opens with `declare(strict_types=1);` (consistent with the project's v2 convention noted in PATTERNS section 8). This file is the only one in `src/source/` that omits it.

**Fix:** Add `declare(strict_types=1);` after the opening `<?php` tag for consistency. Behaviorally a no-op (the class only declares `const`s), but the inconsistency invites copy-paste drift.

### IN-02: `KnowledgeBase` interpolates table/column/join-table names directly into SQL

**File:** `src/source/KnowledgeBase.php` — multiple sites: `:180`, `:205`, `:222-223`, `:281`, `:286-298`, `:294-298`, `:317`, `:511`, `:532-533`, `:552-553`, `:620-623`

**Issue:** Backticked table/column names are concatenated into SQL strings (`'SELECT COUNT(*) FROM `' . $sourceTable . '`'`, etc.). `$sourceTable` originates from `@ORM\Table(name: '...')` regex on operator-supplied PHP source files, `$column` / `$col` from the same parser, and `$joinTable` from operator-edited `mapping.yaml`. None of these go through `isSafeIdent()` at the call sites (only `loadAllColumns()` filters on it).

**Threat model context:** plugin is dev/staging only via `NeverProductionTrait`; inputs are operator-controlled; this is a verbatim port from v1 which already shipped this way. Acceptable per the threat model documented in `CLAUDE.md`. Worth noting because the v1 ports preserve the trust boundary.

**Fix (defense in depth, optional):** route helper-method writes through `LegacyDbService::queryScalar` plus a shared `isSafeIdent()` guard at the helper boundary (e.g. `fetchSamples`, `renderTableColumns`), so that an unsafe identifier is rejected with a `Craft::warning` rather than reaching MySQL.

### IN-03: `Plugin::config()` component-line alignment is inconsistent

### IN-04: `KunstmaanPageStructureScanner::scanPageEntity` swallows resolver failures with two separate `Craft::warning` paths

**File:** `src/source/KunstmaanPageStructureScanner.php:197-215` and `:131-148`

**Issue:** The `try/catch` blocks for `tableResolver->resolve()` distinguish `InvalidArgumentException` (silently sets `$tableName = ''`) from `Throwable` (logs via `Craft::warning`). For a Page entity that the resolver legitimately can't map (most pages will fall through `DetailTableResolver`'s 4-tier resolution and hit the final `throw \InvalidArgumentException`), this means the scanner produces a record with `tableName: ''` and no log entry — the operator has no signal that a Page entity dropped its table mapping. Downstream `pageStructure.json` consumers will see empty `tableName` strings.

**Fix:** Optional — emit a `Craft::info` (not warning) when `InvalidArgumentException` fires, so the operator can grep storage logs for unresolved page entities. Behaviorally fine as-is; this is just an observability nit.
