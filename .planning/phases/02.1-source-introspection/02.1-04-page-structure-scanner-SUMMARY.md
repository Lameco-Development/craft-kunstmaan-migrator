# Phase 02.1 Plan 04: Page-Structure Scanner Summary

**One-liner:** Greenfield AST-based scanner that reads `src/Entity/Pages/*.php` (`getPagePartAdminConfigurations()` / `getPageTemplates()` / `getPossibleChildTypes()` / `#[ORM\DiscriminatorMap]`) plus `config/kunstmaancms/pageparts/*.yml` (allowed page-part classes per context) using nikic/php-parser — produces the per-Page-entity structured record consumed by Plan 6 `pageStructure.json` and Plans 7-8 page-part proposal rows.

## What Shipped

### `src/source/KunstmaanPageStructureScanner.php` (615 LOC)

Final Yii Component with two `public ?TypedProperty` injection points:
- `?KunstmaanSourcePathResolver $pathResolver` — D-33 source-path resolution
- `?DetailTableResolver $tableResolver` — Plan 02-03 FQCN → legacy detail table

**Public surface:** `scan(): array` — orchestrates the full per-FQCN-keyed structured record emission per `<interfaces>` contract.

**Private helpers (5):**
- `scanPageEntity(string $phpPath): ?array` — composes FQCN + tableName + contexts + templates + possibleChildTypes + discriminatorMap for one entity file.
- `scanPagePartsYaml(string $sourcePath): array` — Symfony YAML reader; returns `contextName → list<{name, class}>` index.
- `extractMethodReturnArray(string $phpPath, string $methodName): array` — AST visitor that locates a `Node\Stmt\ClassMethod` matching `$methodName`, finds its first `Node\Stmt\Return_` whose `expr` is a `Node\Expr\Array_`, and reconstructs the PHP value via `arrayNodeToPhp()`.
- `extractDiscriminatorMap(string $phpPath): array` — AST visitor scanning `Node\Stmt\Class_` `attrGroups` for an `Attribute` resolving to `ORM\DiscriminatorMap` / `Doctrine\ORM\Mapping\DiscriminatorMap` / any `\DiscriminatorMap` suffix; returns the discriminator-value → FQCN map.
- `extractClassFqcn` / `parsePhpFile` / `arrayNodeToPhp` / `scalarNodeToPhp` — AST plumbing helpers.

### `composer.json`

`nikic/php-parser` promoted from transitive (already present at v5.7.0 via Symfony) to direct `require`. Locks the AST library against future Symfony version drift (advisor lock-in per `<must_haves>`).

### Auto-fixed Issues

**1. [Rule 1 – Bug] `composer validate` fails without `--no-plugins`**

- **Found during:** Task 1 verification.
- **Issue:** The plan's `<verify>` command runs `composer validate --no-check-publish` bare. That call hits `craftcms/plugin-installer`'s known `Filesystem.php line 519: $from (./vendor/craftcms) and $to (...) must be absolute paths` error. The same issue was already documented and dodged in Phase 1 / D-22 (`composer validate uses --no-plugins to dodge craftcms/plugin-installer Filesystem absolute-path error`).
- **Fix:** Used `composer validate --no-check-publish --no-plugins` per the established Phase 1 / D-22 precedent. Functional outcome identical; the plugin-installer is not relevant to composer.json structural validation.
- **Files modified:** none — process-level adjustment only.
- **Commit:** `25052a1` (Task 1).

**2. [Rule 1 – Bug] Docblock string `include/require` would fail the security grep**

- **Found during:** Task 2 verification.
- **Issue:** The plan's `<acceptance_criteria>` includes `grep -c "include\|require[^_]" ... returns 0` to assert no code-execution primitive runs against source files. My initial draft had two docblock occurrences explicitly stating "NEVER include/require" as a safety claim, and "never include/require, never eval" — both literal grep matches despite being negative/documentary references, not actual code.
- **Fix:** Reworded the two docblocks to express the same security claim without the grepped tokens ("read with file_get_contents and tokenised — never executed, never evaluated"; "bytes are read and tokenised, never executed or evaluated"). Functional code unchanged; security invariant unchanged; grep now returns 0.
- **Files modified:** `src/source/KunstmaanPageStructureScanner.php` (2 docblock comments).
- **Commit:** rolled into `7b7770c` (Task 2).
