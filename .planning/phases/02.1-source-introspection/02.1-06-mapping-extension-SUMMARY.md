# Phase 02.1 Plan 06: Mapping Extension Summary

**One-liner:** mapping.yaml grows a `kind: pagePart` row type alongside existing column rows (D-34); MappingFile::merge() identity tuple becomes kind-prefixed with the page-part branch keyed on STRUCTURAL ONLY tuple (W1 fix — prevents idempotent re-run row duplication when analyze emits empty targetEntryType then operator fills it then next analyze re-emits empty); MapController grows a two-mode walker that branches on row kind first, with the column flow (D-05 + D-06) preserved verbatim and a new compact block + Matrix block-type picker for page-part rows.

## Implementation Notes

### Task 1 — MappingFile schema extension

`src/mapping/MappingFile.php` grows three things:

**`buildPagePartRow()`** — new public method emitting the D-34 reference shape:

```php
public function buildPagePartRow(
    string $pagePartClass, string $sourceTable, string $parentPageClass, string $context,
    string $targetEntryType, string $targetMatrixField = '', string $targetBlockType = '',
    array $fields = [], string $confidence = '', string $rationale = '',
): array
```

Emits `'kind' => 'pagePart'` + the structural identity fields (pagePartClass, parentPageClass, context) + the operator-fillable targets (targetEntryType, targetMatrixField, targetBlockType) + `'fields' => $fields` + `'status' => 'needs-review'` per D-35 (no auto-promotion in v1.0 — page-part → block-type is a domain decision, no deterministic heuristic strong enough).

**`buildRow()`** — patched to set `'kind' => 'column'` as the first array entry. Forward-compat per D-34: makes the kind discriminator explicit on column rows so the rubber-stamp loop and merge() identity tuple can branch reliably. Existing callers (HeuristicProposer, LlmClassifier, AnalyzeController) don't need changes — they keep calling `buildRow($proposal, $initialStatus)` with the same positional arguments.

**`merge()` identity tuple — kind-prefixed via new `identityKey()` helper:**

```php
private function identityKey(array $row): string
{
    $kind = (string) ($row['kind'] ?? 'column');
    if ($kind === 'pagePart') {
        // STRUCTURAL ONLY — no targetEntryType (W1 fix)
        return 'pagePart|' . ($row['pagePartClass'] ?? '')
            . '|' . ($row['parentPageClass'] ?? '')
            . '|' . ($row['context'] ?? '');
    }
    return 'column|' . ($row['table'] ?? '')
        . '|' . ($row['column'] ?? '')
        . '|' . ($row['targetEntryType'] ?? '');
}
```

The page-part branch deliberately omits `targetEntryType` from the key. This is the W1 fix from plan-checker. Page-part identity is the structural triple "which class lives in which context under which parent page"; the `targetEntryType` is an operator decision filled in via the rubber-stamp loop. Without the structural-only key, the idempotent re-run flow (analyze → empty → operator fills → analyze re-runs → empty again → tuple mismatch → DUPLICATE row appended) would balloon mapping.yaml on every analyze re-run. With the fix, the structural tuples match across re-runs and the existing operator-filled row is preserved verbatim per Phase 2 / D-04 skip-existing semantics.

**Backward compatibility:** rows without an explicit `kind:` field default to `column` on load (the `(string) ($row['kind'] ?? 'column')` fallback is uniform across `buildRow`, `merge`, and `MapController`). Phase 2 mapping.yaml files (which never wrote a kind field) load + walk + merge unchanged. Existing Phase 2 tests stay green.

**`loadProposed()` and `setStatus()`** required zero changes — both are kind-agnostic. Page-part rows always start `needs-review` per D-35, so loadProposed walks them automatically. setStatus mutates the fixed key set (status / rationale / targetHandle / handler) which works identically on both kinds; the page-part `[r]emap` flow needs a different write path for `targetBlockType` (handled in Task 2).

### Task 2 — MapController two-mode walker

`src/console/MapController.php` grows:

**Kind-branch in `runInteractiveLoop`:** The main `foreach ($walkOrder as $rowIndex)` block now dispatches on `(string) ($row['kind'] ?? 'column')` FIRST, then delegates to one of two helpers. To keep the kind-branch readable without duplicating ~50 lines per arm, the existing column-row dispatch was extracted verbatim into:

**`dispatchColumnRow($path, $rowIndex, $row, $position, $total): ?int`** — the existing Phase 2 / D-05 + D-06 flow byte-for-byte (renderRowBlock + select(a/d/r/s/q) + setStatus on accept/drop, runRemapPicker on remap, no-op on skip, return ExitCode::OK on quit). Returns ExitCode::OK on quit, null otherwise.

**`dispatchPagePartRow($path, $rowIndex, $row, $position, $total): ?int`** — same a/d/s/q semantics as the column branch (atomic per-keypress writes preserved per D-07). [r]emap leads into runRemapPickerForPagePart (block-type picker) instead of the handler+handle picker. The remap branch persists `targetBlockType` via writePagePartBlockType() — a direct writeAtomic call that overwrites the row's targetBlockType + flips status to accepted (setStatus only mutates status/rationale/targetHandle/handler, so page-part-specific fields need their own write path; the writeAtomic primitive is the same one setStatus uses, so D-07 atomic-always-on is preserved).

**`renderPagePartRowBlock($row, $position, $total)`** — D-05-style compact block tailored to page-part fields:
- Header: `[N/total] HeaderPagePart in NewsPage context 'main'`
- 60-char separator
- Proposed line: `→ targetEntryType.targetMatrixField (block: targetBlockType)  (confidence: ...)` with `(unset)` placeholders when fields are blank (operator-friendly visibility)
- Source table line
- Rationale line
- Each `fields[]` entry inline: `  targetHandle ← sourceProperty (handler)`
- Closing 60-char separator

**`runRemapPickerForPagePart($row): array`** — block-type picker:
1. Resolve available block-types via `blockTypeHandlesForMatrixField($entryType, $matrixField)` (live FieldLayout walk: getEntryTypeByHandle → getFieldLayout → getCustomFields → match by handle → getEntryTypes() on the Matrix field, since Craft 5 Matrix block-types ARE entry types).
2. If discoverable: build a numbered picker with `[t]ype manually` + `[b]ack`; pre-empts the no-block-types case by falling straight through to type-manually.
3. Returns the row with `targetBlockType` updated (or unchanged on cancel). Per-field handle pickers for the nested fields[] array are out of scope for v1.0 — TODO(phase-3) note placed in the docblock.

**`typeManuallyBlockType`** — re-prompts in `while(true)` until valid or back (T-2-18 mitigation pattern preserved). When discoverable block-types exist, validates input against the live list. When NO block-types are discoverable (entry type / layout / matrix field missing in Craft), accepts any non-empty input — operators can author against an un-provisioned Matrix field that hasn't yet been set up in Craft. Empty input or "back" cancels.

**`blockTypeHandlesForMatrixField`** — sibling to Plan 04's `fieldHandlesForEntryType`. Walks the live FieldLayout, finds the Matrix field by handle, enumerates its `getEntryTypes()` block-type handles. Defensive: returns [] on any missing piece (entry type, layout, field, getEntryTypes method) so the picker degrades to type-manually rather than crashing.

**`writePagePartBlockType`** — helper called from the page-part [r]emap branch. Re-reads the YAML, updates `proposals[$rowIndex]['targetBlockType']` + flips `status` to accepted, and writes via `mappingFile->writeAtomic(...)` — the same atomic-always-on primitive setStatus uses (D-07 tmp+rename). Returns false if the row index is missing (caller's bug, surfaced as a stderr FAIL line in the dispatch branch).

**Phase 2 invariants preserved verbatim:**
- D-07 atomic per-keypress writes — every `[a]/[d]/[r]` calls writeAtomic (via setStatus or writePagePartBlockType); `[s]` skips without mutating; `[q]` returns ExitCode::OK with the persisted-decisions reminder.
- D-08 walk-order locking — `$walkOrder` computed once at top of runInteractiveLoop; each iteration re-reads `MappingFile::load($path)` for current state; the walk order itself is immutable.

The four existing MappingFile tests covering D-04 skip-existing semantics + the (table, column, targetEntryType) identity tuple still pass without modification.
